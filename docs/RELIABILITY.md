# Reliability and safety notes

- **Allocation:** progressive allocation reserves one available agent and one eligible borrower in one SQLite immediate transaction. Predictive allocation reserves only a borrower; an answer atomically claims an `AVAILABLE` agent. If no agent can be claimed, the answered call is terminal `ABANDONED_NO_AGENT`.
- **Duplicate work:** allocation filters borrowers with active calls and safely requeued work. `claim_queued()` resumes a pre-provider reservation in place, preserving one call per borrower. This sample does not model legal contact windows or suppression lists.
- **Events:** `(provider, event_id)` is the idempotency key; `(call_id, provider, seq)` is unique. Repeated IDs return `DUPLICATE`; old sequence values return `STALE`; invalid transitions return `INVALID_TRANSITION`.
- **Safety:** predictive output is a proposal only. Safety applies configured rate/concurrency caps. A fresh estimate below the minimum sample count falls back to Progressive dialing; stale inputs pause pacing. Unhealthy providers also pause when provider health is below the configured minimum, while excessive provider failure or timeout rates can reject the proposal. Its answer-capacity bound uses a 50% answer-rate prior and a 2.33-sigma one-sided margin to account for batch variance. The abandonment estimate is a deliberately simple illustrative heuristic, not a regulatory calculation.
- **Provider failure:** new calls are allocated only when a mock provider is available. An outage does not automatically fail an already-ringing call; the provider event or timeout determines its outcome. Timed-out calls may enter `RETRY_WAIT` with one bounded retry and deterministic exponential backoff (5 seconds, then 10 seconds under the default policy). Retry claims reuse the same call and borrower while atomically reserving an available agent. Predictive pacing scales its proposal by provider health, and the Safety Controller pauses on unhealthy provider inputs. This is a local simulation policy, not a production retry scheduler.
- **Worker recovery:** `Store.recover()` requeues only calls still in `RESERVED`, because no provider attempt was started. It releases an associated agent only if that agent is still `RESERVED`; an agent that became `PAUSED` before provider initiation stays paused. Calls in `INITIATED`, `RINGING`, `ANSWERED`, or `CONNECTED` become `UNCERTAIN`; assigned agents are paused and borrowers remain protected until a late provider event reconciles the outcome. A late `CONNECTED` event restores the associated agent only while it remains `PAUSED`; otherwise the event is rejected. A late `COMPLETED` event moves the quarantined associated agent to `WRAP_UP`. For predictive calls recovered immediately after `ANSWERED`, no agent may yet be associated; a late `CONNECTED` event is rejected and the call remains quarantined because automatic agent assignment cannot be proven safe. Terminal `ABANDONED_NO_AGENT` calls are not recovered or redialed. This avoids redialing a call that may already have reached a borrower. It is a local recovery hook, not process supervision or a distributed scheduler.
- **Metrics:** provider attempts come from persisted `calls.attempts`, including retry initiations. Answered no-agent abandonments count as answered only when an `ANSWERED` provider event is present. The standalone `SimulationMetrics.from_states()` helper retains a backward-compatible state-derived attempted value when callers omit the optional attempt count; final state counts alone cannot distinguish logical calls from provider attempts.
- **Load test:** `uv run python -m smartdialer.cli load-test --agents 32 --borrowers 32 --workers 16 --seed 42` races independent SQLite connections using temporary synthetic data. A pass means the expected number of unique reservations completed without worker exceptions. The reported rate varies with machine and filesystem and must not be read as production capacity.
- **Local smoke observations:** recorded runs include 32/32 reservations at 32 agents/borrowers and 16 workers, with zero duplicates or worker errors; separate runs reported about 29.14 reservations/second (1.098 seconds) and about 40.31 reservations/second. At 1,000 agents and borrowers, three runs with 8 workers each reserved 1,000/1,000 with zero duplicates and errors (24.89–25.22 seconds; about 39.65–40.17 reservations/second). Runs with 16 workers intermittently failed to acquire SQLite's write lock (`OperationalError: database is locked` at `BEGIN IMMEDIATE`); one observed result was 998/1,000 reservations and 2 worker errors, while reruns also passed. These are machine/run-dependent observations, not equivalent benchmark results or production-capacity claims; the exact source revision was not recorded and they were not independently rerun during this documentation update. Use 8 workers for a repeatable 1,000-agent smoke check in this environment; the 16-worker variation reflects contention and is not a capacity guarantee.
- **Logs and privacy:** no names, phone numbers, email addresses, or raw dataset rows are logged. Only synthetic identifiers and aggregates should enter simulator output.
- **Limitations:** real-time contention, multi-host recovery, retention, provider callback authentication, timezone contact policy, opt-out/suppression enforcement, and compliance review are outside this prototype.
